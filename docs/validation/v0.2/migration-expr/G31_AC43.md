## Scope

T-020 is a build-time compatibility task. The compatibility translator lives under `packages/domain-harness-compiler/src/compat/v01-expr/` and only rewrites frozen v0.1 `invoke.expr` nodes. It does not modify Runtime assembly, Tool execution wiring, persistence, or the sibling script-migration task.

For every legacy expression invoke, the translator:

1. fails closed when expression source is missing;
2. derives a deterministic `sourceIdentity` from expression source plus legacy input/timeout semantics;
3. derives the synthetic Tool id from workflow id + state id + source identity;
4. replaces `invoke.expr` with `invoke.tool` while preserving `input` and `timeoutMs`;
5. emits an effect-free synthetic Expression Domain Tool descriptor containing the expression source and permissive JSON output schema used by the existing portable `ExpressionToolExecutor`.

Filesystem location is intentionally not part of identity. The same authoring content therefore remains stable when the package is relocated.

## G31 reference scenario

The committed fixture is intentionally non-trivial. One expression derives three output fields and branches on `input.score >= 80`; the validation executes both sides of that branch:

- `alpha`: score 91 → approved branch, derived weighted score and summary;
- `beta`: score 63 → review branch, derived weighted score and summary.

The legacy side executes the frozen v0.1 `StepDispatcher` `invoke.expr` path. The migrated side executes the generated descriptor through the portable `ExpressionToolExecutor`. Both use the same deterministic input and logical clock.

The comparison is limited to contract-relevant observable branch/state classification and output. It deliberately does **not** compare synthetic Tool ids, internal run ids, persistence layout, timestamps, or other non-semantic implementation details. This selected scenario emits no Domain Messages, so emitted-message comparison is not applicable.
