## 1. 产品目标和使用者

DomainHarness 是嵌入 Domain App 的语言原生 SDK。0.11.3 的目标不是自适应 UI 引擎，而是借助领域知识和已验证业务能力，把未确定的用户需求逐步转化为可处理的、确定的领域意图。面向应用使用者减少表达、选择和确认成本；面向 LLM、Agent 和手工开发者提供真正可直接复用的通用标准实现，让生成者主要实现领域专有知识、规则、专业计算和流程组合。

产品价值：系统先分析可确定的内容和真正不确定的关键决策，再尽可能生成候选意图、方案、预填内容及动态表单；用户选择、修改或补充即可推进，不必从零编写需求，不必逐项或按固定顺序确认。完整、明确的意图应走快速路径；交互是必要时使用的能力，不是所有业务的强制入口。

## 2. 原则及产品要求

以下 ID 为可追踪产品需求；具体 Class、API、Package 结构、数据类型及状态机算法留 L2，不预设第二 Runtime。

| ID | 必须满足的产品行为 |
|---|---|
| SI-P01 知识驱动 | 根据领域目标、真实业务知识、权威事实、适用规则和候选流程分析意图；支持已确定、部分确定、歧义、未知、矛盾、不适用、无法确定的情况。业务专有类型、知识和规则由 Domain Package 定义；不强制全领域统一 Goal/Intent/Fact ABI。 |
| SI-P02 关键决策优先 | 优先请求改变目标、业务流程、方案或实质结果，以及可确定多项关联内容、确需用户决定的高价值事项。可可靠获取/推导的内容不要求用户再次输入；硬政策不可由确认绕过。根据当前情况动态选择下一关键决策，允许一次解决多个关联事项、跳过无关步骤；不要求固定顺序或逐字段确认。 |
| SI-P03 候选优先 | 优先生成合法候选意图、可选方案、推荐内容、预填值及依据；根据领域约束和真实数据筛选、推导及更新。用户可以选择、修改、表达没有合适选项、补充或拒绝；未知/不完整候选集不冒充完整，不能虚构事实/方案。 |
| SI-P04 动态表单 | 用预生成模板和按需动态生成的语义表单内容、字段、选项、说明与约束，支持多步骤交互；用户当前选择改变后续内容、分支及必要性。步骤多少由真实意图决定，允许零澄清；动态表单服务意图确定，不是为了动态 UI。 |
| SI-P05 最小确认 | 用户的明确输入、关键选择或提交可构成意图确认；不强制另加最终确认或逐项确认。对未确认的重大推断、冲突及必要选择不得擅自视为确定。区分已表达的偏好、系统推荐、适用默认、权威事实、推导和未知。能够查看和修改适用内容；修改使受影响的候选/确认失效。 |
| SI-P06 单意图多轮 | 一个逻辑意图可跨多个用户交互轮次推进，保留有效信息和关联执行，拒绝重复、过期或不匹配的响应；保持同一逻辑请求的根业务预算，不因等待/重新提交而重置。支持等待、继续、修改、拒绝、取消及终结；应用运行期状态不承诺重启恢复。 |
| SI-P07 多独立意图 | 同一 Domain App 可同时推进多个独立意图。等待只影响当前意图对应的 Workflow 和依赖它的执行，不能使无关 Workflow 或整个应用停止。各意图的输入、状态、预算、候选、确认、取消、结果和拥有资源不串扰；显式依赖/共享资源冲突仍按业务规则。非强制线程并行，不要求每意图一个 Actor。 |
| SI-P08 自然语言入口 | 保留文本框作为初始入口和结构化交互无法表达需求时的兜底。支持领域范围内程序识别，充分确定时直接使用，不确定时走结构化澄清或明确拒绝。允许最小 LLM 接入接口或 mock；本版不要求实际模型调用、推理或 provider，0.11.5 完成。自然语言及 mock 输出不是授权或可执行代码。 |
| SI-P09 语义交互与客户端 | 提供与 UI 技术无关的输入、说明、结构化字段/约束、预填/候选选择、比较、确认、拒绝、取消语义；按领域需要支持文件引用等输入输出。应用/客户端选择 Form、Selector、Table、Wizard、Dialog、Chat 等呈现方式，适配不同客户端，语义等价降级或明确不支持。SDK 不提供通用 UI 框架，不要求所有客户端均实现全部呈现。 |
| SI-P10 Workflow 衔接及授权 | 复用 0.11.2 Intent Recognition / Handling 的业务职责；澄清细化 Recognition；已确定意图进入 Handling，若处理发现新的意图不确定性则可重新澄清，已确定意图内的方案选择与实际业务授权保持职责。意图确认不等于操作授权；保持 .2 PREAUTHORIZED/USER_APPROVAL、PER_CALL/SESSION、范围/内容/版本检查、attempt/receipt/readback/UNKNOWN。未满足必要前置条件不得产生 Effect，不重复要求已合法预授权的批准。 |
| SI-P11 标准实现优先 | SDK 为真实有复用价值的非领域专有重复职责交付实际可用的标准实现：意图/决策/候选组织、动态澄清和表单交互、响应校验、确认和失效管理、局部等待与组合等共同能力；不得仅交付接口、抽象类、空壳或两个领域各自重写通用代码。复用既有 SDK/原生语言能力；通过 Package/Element/Function 实现职责内聚、可组合、可维护的标准化，不要求每个字段/步骤/helper 一个 Element 或 Workflow。业务提供领域规则和专有类型，具体抽象粒度由 L2 根据真实用途确定。 |
| SI-P12 Agent-first 交付 | SDK 优先方便 LLM/Agent 发现、理解、生成、组合、修改、测试与维护，同时兼顾人手写代码。统一原生 TS API、清晰类型/命名/错误语义、短默认路径、可直接用的实现；权威规范、Skill 导航、TSDoc/JSDoc、实际可运行用例及独立消费者证据。不增加必需 DSL、生成器、专用 Agent API 或第二 Runtime；SDK 不承担 Package/Element 生成正确性的证明。 |

## 3. 意图确定过程与边界

- 完整输入 → 领域识别与校验 → 已确定意图 → Handling。若需要澄清：识别未确定关键决策 → 生成候选与当轮结构化表达 → 用户选择/修改 → 分析、推导与必要重新计算 → 只继续必要澄清。用户可拒绝或终止；没有合法候选、事实不可得、工具错误、不可行和 UNKNOWN 必须保留各自语义，不能机械地都转 ASK。
- 多轮中的事实应区分来源、适用范围、相关版本、用户断言与系统推导（按业务需要表达）。冲突不静默覆盖；允许修订目标/偏好但不能绕过硬约束。依赖无法可靠证明时可保守重算受影响意图，不强制通用 truth maintenance engine。
- 单次澄清是业务交互，不是 KDP 全局状态。用户等待不占用线程进行阻塞等待；不必保留整个 Actor 或强制固定恢复算法。取消阻止后续关联操作并按所有权清理；已提交或可能提交的外部效果按 .2 真实 readback/UNKNOWN 处理，不承诺回滚或全局 exactly-once。应用关闭遵既有 KDP 收敛及资源退出合同。
- UI 语义与呈现分开；客户端不替领域判断真实性、业务授权或 KDP 状态转移。独立意图不是全局对话中的一串不区分归属的消息。用户明确提交的同一意图仍需验证当前适用事实与授权条件。
- SDK 的职责是提供通用实现而不是替领域生成者编写专业逻辑或在运行期验证 Package/Element 结构。生成期可预制模板、知识、规则、候选生成函数；运行时动态产生实例数据、选项与流程决策，不要求运行时生成/执行 TS 代码。

## 5. 真实应用场景

以已有 #1720 的两个真实领域为首选验收素材；这属于 R1–R6 推导的验收设计，不是 Owner 指定新的领域政策。保持已有冻结政策和独立 oracle；如增加业务功能需有需求依据及独立验证，不为展示 SDK 虚构业务。

**媒体档案**：检测实际文件、权威归属与适用政策；已可获取的技术元数据不询问用户；合法归档目标及处理提案优先，必要时澄清缺失的关键选择。完整性、真实解码、源容器时长及独立副本核验继续有效（原 8 MiB/10s/320 规格不由表单绕过）；修改源、目标或适用范围后，受影响结果与确认失效。真实归档效果绑定原件、访问副本和 scope，拒绝/越权不产生可见记录，实际 Host 独立读回。

**维修工序排程**：先取得已知订单、工序、日历和资源条件，领域知识保证检查→维修→质检；根据缺失的关键目标或约束生成候选；用户修改后重算且独立验证。原 7/10 时段分别是正常与停机不同政策下的证据，不能当同约束下的两个可选方案。区别不可行、未证最优、未知和技术失败；保留现有 planning-only 范围，不为演示确认而虚构 dispatch/publish Effect。

**多意图场景**：在同一实际应用激活中，意图 A 等待关键选择时，独立 B、C 可继续识别、完成或处理；向 A 返回选择只能推进 A 的关联执行，不能改写 B/C；A 的拒绝、修改、取消不关闭无关 Workflow。若 B 明确依赖 A，则仅有关分支等待。

## 7. 前置基础专项及进入 L2 的门禁

执行顺序经 R7 调整：先固化本 PRD/L1 和 #1722 全局规范，经限定独立审核合入并正式冻结；再以冻结 WHAT 为依据审核 .0–.2 的 Standard 复用、Agent 消费便利性及基础 Workflow 关联等待、独立意图、多轮预算；按真实根因及所属版本修正、独立增量审核；最后进入 .3 L2。L1 不需要等待基础优化才能定义，但 L2 须使用优化后确证的基线。

前置专项不是新的全面重构、不是对旧已验收功能全量重跑，也不提前实现 .3/.5/.6。R5 已记录已观察的 README/公开类型文档不完整和 Workflow 接线风险；风险需实测才能判定缺陷。对真实已有应用中的重复通用逻辑，应分析实际跨用途复用价值、依赖闭包、公开 API 与 Agent 生成/维护便利性；确认属 SDK 的共同能力就由归属版本提供实际标准实现，而非让后续 Domain App 重新生成。单次限定工作，不开启持续 Agent。

审核通过前不宣布 L1 正式冻结；独立审核仅评审本产品合同、需求追踪、范围和 Oracle，不启动 L2、Task DAG、源码实施、CI、本地 Agent、后续版本或发布。正式冻结后若出现产品需求变更，按 Owner 明确裁决更新合同及验收，不由基础优化自行改变产品范围。
