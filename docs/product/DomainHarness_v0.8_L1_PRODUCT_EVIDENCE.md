**Primary user A: SDK consumer / application integrator.** Trigger: deploy or upgrade a narrow-domain app. Job: select exact verified package closure, resolve needed capabilities/Kind handlers and start an authorized runtime. Existing workaround: custom glue and runtime-private adapter logic. Pain hypothesis: compatibility drift and changes not independently replayable. Observable acceptance: same pinned assembly yields the same admitted behavior; invalid dependency and handler drift are refused before effects.

**Primary user B: Domain Package author.** Trigger: add a Rule/Decision/Workflow/Operation to one domain app. Job: express schema, relations, required capabilities and optional callable operations without modifying Kernel. Workaround: hard-coded runtime dispatch or per-domain plugin glue. Pain hypothesis: every new semantic Kind forces risky Kernel changes. Acceptance: one new versioned declared KindImplementation can be accepted via a verified Standard/Business Package; unsupported material Kind is rejected.

**Primary user C: Domain App / UX integrator.** Trigger: end-user intent, resume after a WAIT or replace an app version. Job: relay typed requests and receive attributable outcomes, without UX or a model owning state/effect authority. Workaround: direct service mutation with ad hoc authorization. Pain hypothesis: unsafe effect duplication/unknown results when interrupted. Acceptance: denial of unauthorized transition and recovery pins maintained; runtime results—not UI state—are authoritative.

These are **developer/consumer archetypes**, not empirically sampled customer cohorts. L1 must record this limitation explicitly.

### 5.1 Chosen narrow consumer Host and trust perimeter (Product acceptance; not asserted implemented)

- **First target:** clean **Node.js TypeScript embedded SDK** consumer using existing monorepo `packages/domain-harness` and Node adapter. Product Host contract = install pinned local/approved packages, authorize publisher/owner and exact manifest/module bytes from a Host-controlled allowlist/trust store, admit finite dependencies, activate/deny, invoke through inherited T002/T004, observe typed receipts. Node version/ABI, loader details, signatures, storage, packaging and exact public entrypoint are L2 decisions backed by real clean-consumer evidence.
- **Trust sequence:** the **Host operator**, not a manifest field, selects trusted package publisher/owner and authorized exact bytes/declarations **before permitting module loading and SDK-mediated execution**. Canonical bytes/hash prove integrity only; independently authenticated provenance/Host allowlist proves approval. Caller-supplied digests and arbitrary selected functions do not confer authority. Host/SDK must refuse tampered bytes, undeclared modules/exports and unapproved publishers before executing their *SDK-mediated* operations.
- **Explicit limit:** ordinary trusted native **JavaScript modules are not sandboxed** by DomainHarness. A Host-permitted import can access ambient file/network capabilities **at module-evaluation time, before SDK Admission**. Without actual Host isolation/restriction, no claim of universal “zero unauthorized effects” or effect-free import is made; the SDK promises to gate **SDK-mediated authoritative State/Effect**, not arbitrary Host process side effects. Test an import-time write/network attempt in a controlled Host fixture, state whether Host blocks it or explicitly counts it as trusted-code risk, and never relabel it as SDK Admission PASS.
- **Negative cases:** forged pre-bind digest, unapproved signer/owner, tampered exact bytes, missing code, unsafe loader path, fake effect authority, post-seal handler mutation. Absence of enforceable Host trust/isolation and native executable wiring remains **NOT_PROVEN**; tests and mechanism belong to technical owners.
- **Scope boundary:** Browser/Expo/Android are **not supported for new B in R1 Product minimum**. Existing accepted v0.7 cross-host surfaces remain **preservation-only** and may not be broken; platform expansion requires a separately evidenced Host authorization/ABI acceptance. Windows/ECF integration is a later designated validation profile, not a claimed second product Host.
