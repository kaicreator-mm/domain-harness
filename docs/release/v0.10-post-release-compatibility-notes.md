# v0.10 post-release compatibility notes

Changes merged to `main` after the v0.10 integration (#1216) that alter
durable layout or caller-visible behavior. Pre-1.0 policy applies: L2
(`DomainHarness_v0.10_L2_ARCHITECTURE_R0.md`, P1-01) states **no pre-1.0
migration**, so nothing below is migrated automatically.

## 1. Governed K docs namespace is stable across BUILDs (#1217, PR #1240)

- **Before:** every K document of a governed deployment lived under
  `v10/k/<subjectDigest>/<tenantId>/v010-k02:…` — a new physical namespace per
  BUILD.
- **After:** governed activations (`activateGovernedV10Build`, or
  `activateV10App` with `deploymentIdentity`) use the stable outer prefix
  `v10/k/deployment:<deployedAppId>:<tenantId>:<appId>/v010-k02:…`, as the
  frozen L2 requires. Activations without a deployment identity keep the
  historical `v10/k/<subjectDigest>/<tenantId>/` prefix.
- **Impact:** K state written by a governed deployment **before** this change
  is not visible after upgrading — including when an old BUILD is restored
  with `selection: 'PINNED_ONLY'`, because the reader now uses the new prefix.
  Occurrence BUILD pins and activation records are keyed independently and
  survive, so an old in-flight occurrence keeps its redirect guard but its K
  instance reads as absent.
- **Action:** drain or finish in-flight governed occurrences before upgrading.
  Retained data stays physically present under the old prefix for audit; no
  tool copies it forward.

## 2. Governed first admission is serialized per occurrence (#1219)

- While an occurrence's first message is `RESERVED`, a different message or
  another BUILD for the same instance is refused
  `OCCURRENCE_RESERVATION_PENDING` with `detail.retryable === true`. Callers
  that previously relied on two distinct messages racing into a brand-new
  instance must retry the refused one after the first settles.
- A crashed writer's held slot can be released only by the Host's explicit
  `recoverReservation(intent, { priorWriterTerminated: true })`; see
  `docs/architecture/V010_GOVERNED_OCCURRENCE_PIN_RECOVERY_PROTOCOL.md` §4.
- New RESERVED pins also bind `intentType`. Reusing the reserved messageId
  with a different bound intent is refused with `retryable: false`.
  Old pins without this field remain readable; no intent is inferred from
  a retry. They can still heal from a matching admission witness, but cannot
  authorize deletion after a denial.
- Only an owner of an intent-bound reservation receiving the Kernel's fixed
  caller-role denial can compensate its pin. Dynamic Guard/schema/policy
  refusals and `terminated` results retain RESERVED, because a concurrent
  evaluation of the same message may still admit. Host slot release does not
  change this rule or cancel in-flight adopters.

## 3. Reservation digest uses the selected kernel's canonical form

Reservation `inputDigest` values written by the first #1219 implementation
used the compiler's `canonicalJson`. For inputs with integer-like object keys
(e.g. `{"2":…,"10":…}`) that digest differs from the kernel's, so such a
legacy `RESERVED` pin never matches its witness. An exact resend computes the
new Kernel digest and refuses `OCCURRENCE_RESERVATION_PENDING` with
`retryable: false`. The §2 Host release changes only the writer slot; it
does not rewrite the stored digest, so resending after release also fails.
Neither API migrates or repairs this legacy pin.

**Action:** before upgrading, drain affected occurrences with the old writer
and settle their pins. If an affected RESERVED pin already exists after an
upgrade, keep its original BUILD and data for reconciliation; there is no
automatic or API recovery for this encoding mismatch. An operator reset of
the deployment/store is appropriate only when its data is explicitly
disposable; never delete an individual pin around potentially admitted K
state. Inputs whose canonical bytes are identical remain compatible with
digest comparison, subject to the old unbound-intent limitation in §2.
