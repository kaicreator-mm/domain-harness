## 2. Architecture selection

Compare A generic runtime DAG interpreter / global capability registry (reject: duplicates native runtime, model could control too much, violates fixed root); B XState machine regeneration per proposal (reject as default: invalidates actor identity, running effects, observer history, requires serializing arbitrary trusted callbacks, no evidence existing runtime supports safe mutation); C existing native Workflow plus bounded mutable *execution structure* inside an explicitly declared region (preferred). XState remains suitable for fixed state/branch/parallel composition; TypeScript native callbacks remain suitable for ordinary workflow. Dynamic region is a reusable Standard composition calling actual functions and child Workflow through the existing root, not a new execution root. Runtime region is intentionally a finite ordered sequence with explicit earlier-result dependencies and recursively generated subregions; no new generic scheduler, expression language, or parallel DAG executor. Existing fixed parallel composition remains allowed. Additional finite dynamic dependency/parallel support only if actual domain evidence requires it and reviewed before implementation.

Core: Definition (trusted immutable native code/data), Execution (task-local running instance, admitted local plan, status, actual facts), Context (projected actual facts+knowledge/function requirements+progress), Proposal (untrusted bounded data or trusted algorithm output validated by the same admission). Data Knowledge and Function Knowledge stay domain-owned. All methods/validation have same semantics for no-model, model-assisted and mixed. Model adapter proposes only. Reasoning is not Model. Tool is a projection of a selected native Function, not another executable identity.

### 2A.2 Three layers, one execution contract

A. Native Workflow Foundation (.1 #1605, .3 #1613 attachment): one root lifecycle/state/admission/ancestor constraints and budgets, execution occurrence identity and semantic progress projection, native Function/child Workflow invocation, pre/run/post/terminal observation envelope, control/cancellation, actual outcomes and lifecycle ownership. B. Domain Workflow composition (.5 uses existing foundations): trusted Definition binds domain goal/input/output, stage/node roles, Data Knowledge requirements (necessary facts/rules/constraints plus explicitly allowed runtime reads), Function Knowledge (direct typed references incl composite Workflow), applicability/guards, data-flow/transition and completion gates, optional mutable region boundary. A declared managed node or subworkflow is executed through shared foundation; existing uninstrumented native helper paths remain legal but do not qualify as observed reasoning steps. Required pre/post gates must have actual reachable execution/validation, not simply listed metadata. Branch/loop/join use existing trusted TS/XState; dynamic child sequences use the same envelope. Parent/child stable I/O, independent completion, delegated constraints, bounded recursion, same root, private internals not leaked.

C. Reasoning composition (.5): use A/B for Context, knowledge/capability selection, deterministic or optional model proposal, bounded local structure admission and adjustment. Reasoning chooses/proposes what to do; Workflow owns actual state transition, execution and validation; shared mechanics must not require Model or ReasoningElement. Model only one request Function; Interaction is composable in either direction. Evidence is actual runtime projection/output, not .7 persistence or Forge authoring.

## 4. Root control and execution admission

One session owns root call/step/depth budget, optional extended reasoning controls required for .5 dynamic execution, abort linkage, active-time/wall deadline and task occurrence. Existing nonreasoning root numeric accounting (including legacy leaf hook reserve) must not change silently. Use a private extension to existing RootBudget/Context rather than duplicate counters in each ReasoningWorkflow. Root control immutable configuration; user-supplied objects snapshot once. Region local limits only narrow inherited quota and scope; repeated plan or child cannot reset root. No public method to add budget; remaining is not a reservation. Reservation synchronous before work, with no await between successful check/debit; no refund of failed/rejected/no-op work. Child execution depth and candidate structural depth both checked, not interchangeable.

Candidate units: retain original calls/steps/depth, add finite work units for each planner invocation, each admission/edit/replan/validation/lookup/feedback iteration and bounded processed record/edge, finite per-candidate byte/depth/node/edge/binding count and total admitted/attempted operations. Also model calls/retries, request/response/context byte caps, output token maximum and optional conservatively enforceable total tokens/cost. Missing usage recorded unknown, not zero; required hard cap unsupported rejects before affected operation. Do not charge arbitrary trusted TS helpers recursively; public bounded composition must meter own controlled work and not allow caller-supplied oversized untrusted plan traversal before checking limits.

Before node entry reserve bounded precheck + business call + required terminal observation/postcheck/cleanup allowance (existing leaf pattern), so exhaustion after effect cannot erase mandatory settlement evidence. Normal new work blocked once stop/deadline/cancel; pre-reserved bounded terminal observation/authorized cleanup can run without opening new business effects. Bounded settlement window and exact root/region accounting are L2 contract items; if no authority result before window ends, local UNKNOWN/non-success with actual facts observed so far, not false rollback/remote settled. Late result during in-process observation window recorded/reconciled; stale outputs cannot advance plan, no promise of post-process delivery (.6). Noncooperative arbitrary trusted sync code cannot be preempted by JS timer; required hard restriction incompatible with such callable must reject at admission, cooperative operations signal abort. No unhandled rejection/detached unobserved promise; explicit lifetime ownership and bounded waiting, existing Interaction unjoined-work behavior must be considered rather than blindly awaiting forever.

Active time monotonic elapsed excluding only actual registered user wait interval, no reset on feedback; wall deadline (if configured) includes wait. Do not pause root active clock while any sibling work in same root is active; default dynamic serial regions make this tractable. Timeout checked before/after awaited work; cancellation prevents subsequent business entry; parallel roots independent. Root abort signal from owner and interaction cancellation same logical root through explicit ownership binding, not global shared signal. No-progress rule meaningful validated state/facts/goal change, not revision or new IDs; finite budget terminates even genuine progress. Final numeric counter table and supported enforcement must be independently reviewable (R16).

## 5. Dynamic region execution structure

### 5.1 Trusted definition vs runtime structure

Region definition: goal, typed input/output, fixed anchors/required gates, initial existing node templates, optional/skippable node policies, allowed native Function bindings, eligible child contract templates, trusted local planner (algorithm and/or Model Function), context projection, pre/post and finish validation, delegation and limits. Native definitions immutable during execution. Model may not introduce a callable, validator, authority, rule or endpoint. Region has occurrence identity, local plan revision and task fact revision; proposals bound to current root/run/region/expected plan+fact revision. Separate reusable definition ID, runtime node ID and attempt ID, including repeated insertion of same node. Runtime-generated child is a new occurrence and structure with a trusted child *contract*, not merely calling a pre-authored fixed child path.

Preferred data representation: bounded ordered local sequence with explicit data dependencies, fixed required anchors and nested regions. Dynamic structure is private task data (not a mandatory serialization format for all Workflow). A candidate edit batch can express:
- insert existing template at permitted position (new occurrence);
- insert new node specifying local capability and input bindings;
- insert generated child using delegated child contract and initial runtime node proposals;
- skip optional pending node with trusted eligibility and evidence; no model-minted output;
- cancel/replace/move pending optional nodes within allowed range; no mutation of past/in-flight history;
- proposed next action/finish/clarification routed to trusted checks. Finish request is not success.

Identifiers from model are proposal-local aliases, mapped to runtime-issued occurrence IDs on admission, not global FunctionRef or authority. Input bindings are bounded literal values or references to explicitly projected context slots and verified earlier node output slots; no eval, property path traversal of arbitrary objects, dynamic SQL, arbitrary code or secret slots. Use explicit slot names/typed domain decoder; actual run input validation occurs before every call. No dependency on skipped node output unless validated equivalent existing evidence is explicitly bound; all reachable paths preserve required anchors and validation, not only membership in a list. For sequential region reject forward references, cycles, unresolved aliases, inaccessible scopes, illegal position, overflow, stale/invalid predecessor; bounded trusted loops are separate from cyclic candidate dependencies.

### 5.2 Admission and runtime

1. Preflight root/local limits and current trusted Definition/goal before planning. Build typed Context. Call deterministic generator or selected Model through root; raw response capped during transport; before JSON parse/recursive construction enforce input bytes and structural depth/item/work bounds. For trusted planner output, require bounded construction interface or documented cooperative bounded generator; don't claim arbitrary JS is sandboxed.
2. Decode finite proposal shape, preserve only accepted data. Check current task/region/revisions and allowed names, allowed positions, node/edge limits and delegated child contract; validate required gates/ordering/dependencies/skip substitutions and business admission. Build candidate copy; no mutate execution on partial rejection. Compare current revisions and atomically adopt within synchronous local state transition after any awaited policy checks; stale proposal rejected, charged.
3. Execute next actual ready node, through existing root leaf/invokeOutcome or child. Precheck current facts, applicability, actual authority, input, dependency and reserve before invocation. On each entered attempt observe actual result/exception/cancel/time/settlement, perform applicable bounded postcheck, record actual facts independent from acceptance. Verified current output becomes admissible to downstream only after relevant gates. Required completion separately checked at parent and root. Preserve six outcomes; explicit skip/progress facts do not create new required public Outcome variant.
4. After observation update Context/progress and fact dependency invalidation; if feedback/actual fact change, invalidate affected output/proposal/approval, preserve unaffected validated results and committed history. Replan only pending/stale work in permitted region (stale completed *result* may need new attempt, historical node/attempt remains). New IDs do not make unknown effects safe.
5. For DY05 generated child, use parent root.child with narrowed depth and region contract. Child planner can produce its own runtime nodes and generated grandchild, within delegated transitive knowledge/capability scope; child result crosses explicit output contract only, private state not implicitly visible. Parent completion independently checked. No second executor or Session.
6. End on verified goal or existing non-success. ASK/WAIT active in-process interaction only where configured; no durable resume. Export actual before/after topology and invocation trace via safe evidence projection, no replay/experience engine.

DY01 candidate generation distinct from DY03 actual insertion; DY02 reuse existing template with fresh occurrence; DY04 skipped is not executed; DY05 nested new structure; DY06 actual remaining-structure revision. Independent tests compare reachable admitted structure and actual call history, not simply a list returned by model.

## 6. Context, validation, effect truth and Interaction

Context input derives from Definition requirements and actual Execution, not model claims. Ordinary TS typed data, no forced global Context class; model projection selected typed slots/descriptions/observations with source/validity and caps; mandatory constraints cannot be silently truncated; no raw application object serialization. Native query outputs feed domain resolver, partial/truncated never proves complete. Data Knowledge immutable definition/version bound by trusted activation; runtime facts/observations/validity mutable, model cannot update rule or cross child privacy. Domain declares fact/knowledge/accepted-output dependencies with scoped occurrence IDs; reuse finite evidence invalidation, missing deps conservative; actual receipt immutable. Need explicit scope identity mapping so sibling reuse doesn't collide. No central Context Manager. Context revision/fact epoch and plan revision separate from actual progress; same values with fresh ID aren't progress.

Apply node pre/post to both fixed and dynamic composed paths; pure node may reuse actual domain invariants instead of duplicated validator wrappers. Proposed observation record distinct from outcome acceptance:
- entered attempt records actual output or exception/cancel/timeout, applicable cleanup, settlement known/UNKNOWN and postvalidation accepted/rejected/not-applicable/unknown; pre-rejected/skipped has no fabricated invocation;
- actual known commit can coexist with plan rejection, obsolete revision or evidence failure; stale valid data must not advance current plan. Actual receipt can invalidate new work, requiring revalidation;
- pending/unknown effect conflicts determined by trusted domain resource/operation semantics, not command ID or model. Before dependent/conflicting new effect, use authoritative readback or block; explicitly authorized independent/compensation path only if domain proves independence/safety. SDK composes the guard/receipt, no universal conflict classifier or centralized permit. Existing real Host .2 remains authority; CAS protects actual transaction not arbitrary cross-resource semantics;
- critical evidence success is separate completion gate; sink error cannot erase commit or unknown; no persistence guarantee. Output explicit non-success plus observed facts without declaring business rollback.

Interaction existing phase/resolve/step/prompt identity and revision remain. Candidate runIn(root,work) attaches existing root and scoped signal, no Session; run(limits,work) creates one root and delegates. User feedback enters trusted task-state reducer, updates fact revision, invalidates affected proposals/approvals/outputs; no direct model state writes. Preserve real prompt correlation/one pending resolve/notify sync and cancel cleanup. Interaction actual waiting interval contributes wait accounting only, root cancellation links appropriately and no unrelated root affected. Reasoning can be called during decide and handling; reasoning can call bounded same-root interaction at a declared checkpoint. Do not recursively call active resolve; sequence/return explicit request to owning scope. L2 must resolve old unjoined-work finally waiting vs new finite settlement using common lifetime contract, including noncooperative test. Progress for fixed XState via trusted semantic projection at observed actor transitions (not external state polling or model self-report); dynamic region reports actual admitted node/attempt states; no raw internal XState snapshot serialization.

## 7. Model protocol and bounded request design

Alternatives official SDKs / AI SDK lower-level: mature transport/schema adapters but dependency/automatic retry/loop/compatibility closure requires preflight.
